# Browser wallet-read recovery

On September 16 at 00:17–00:18 UTC, Chrome requests from `farm.pagzi.tech` reproduced the reported `Failed to fetch`. The official public RPC returned HTTP 429 with `Access-Control-Allow-Origin: *,*`. Chrome rejected this invalid CORS response and hid its HTTP status. A successful `eth_chainId` did not establish availability: subsequent block and contract reads still failed with three-second spacing. No `Retry-After` header was observed. Later official requests succeeded again, so this is evidence of a temporary upstream limit, not a permanent path or origin restriction.

The [official connection documentation](https://docs.robinhood.com/chain/connecting/) describes public endpoint rate limits. [PublicNode](https://robinhood.publicnode.com/) publishes the free Robinhood mainnet endpoint `https://robinhood-rpc.publicnode.com/`. This provider passed chain ID 4663, a pinned reviewed NFT runtime check, and real Chrome block/plant-fee reads with valid CORS headers. Node evidence is [publicnode-read.json](snapshots/rpc-network-2026-09-16/publicnode-read.json); private browser traces remain under `.local-deploy/network-read-review/`.

Version 2.9.2 uses PublicNode for public reads, with the official URL retained as provenance. Website CSP, local serving, Tampermonkey origins and native extension permissions explicitly allow it. No API key, paid provider, proxy or wallet-signing route is introduced. Runtime, chain, pinned-block, ownership and transaction checks are unchanged.

Recognizable network failures and timeouts join bounded rate-limit retries. A shared cooldown pauses queued work, and requests retain their original block tags. Deterministic reverts, invalid responses and wrong-chain observations are not turned into successful reads. An incomplete UI refresh keeps the previous complete snapshot and its original time; it never merges old balances with new plots or authorizes an active-plan step.

A full 26-plot browser check then exposed a separate provider constraint: many individual calls kept the pinned block open too long. A bounded comparison at [head 64,081,224](snapshots/rpc-network-2026-09-16/recent-window-check.json) found the same FEE read successful at head and head minus 64, but rejected at head minus 128 and 256 with an archive-access error. The exact boundary was not established. Free recent state is adequate only while reads finish promptly; the app must never replace individual failed reads with latest-state values. A 20-item batch returned all 20 results successfully. Version 2.9.2 therefore batches up to 20 read-only calls, maps replies by request ID, and retries only failed transient items. Cosmetic metadata has a separate bounded queue so it cannot delay remaining pinned contract reads.

The completed batched build refreshed both configured wallets (26 plots) in real Chrome at block 64,084,455 on September 16, 00:37 UTC: 18 HTTP requests, zero read/metadata/CORS errors, and a successful calculator result. All wallet state requests used the same block tag. This pre-deployment test used the local website with real public network calls; the production origin is checked separately after publication.
